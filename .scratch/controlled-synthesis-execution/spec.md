# Deepen controlled synthesis execution

**Status:** Implementation in progress
**Triage:** Active; do not dispatch another implementation agent
**Tracker:** [SEC-6 — Deepen controlled synthesis execution](<https://linear.app/kenneth-second-brain/issue/SEC-6/deepen-controlled-synthesis-execution>)
**Linear document:** [SEC-6 — Controlled synthesis execution specification](<https://linear.app/kenneth-second-brain/document/sec-6-controlled-synthesis-execution-specification-16ad384e57aa>)

## Problem Statement

As a vault owner, I need concept synthesis to be powerful enough to reorganize my interpretation while remaining unable to damage source evidence or unrelated vault content. The previous executor boundary was too shallow: the direct adapter received bulk source and concept text and returned arbitrary path strings, while the Codex harness ran an arbitrary command and trusted self-reported JSON instead of validating what changed in an isolated workspace. Validation recognized only the current batch’s sources and did not prove citation ranges, timestamp links, symlink safety, normalized path uniqueness, or unexpected deletions.

This means a malformed, confused, or compromised executor can produce unverifiable concepts, escape the intended `Concepts/` boundary, cite nonexistent evidence, or report a change set that differs from its actual filesystem effects. It also forces the batch orchestrator to coordinate executor-specific behavior instead of consuming one fully validated synthesis result.

## Solution

Deepen synthesis into a single `second_brain.synthesis` package with one stable public contract. Batch orchestration supplies only the batch identifier and successfully prepared batch sources to `SynthesisRunner.run`; the package owns catalog loading, immutable provenance discovery, candidate-workspace creation, adapter execution, normalization, validation, and failure classification. It selects either the DeepSeek or Codex adapter behind the same internal seam, observes that adapter through its real execution mode, normalizes the result into one change-set model, and validates the complete result before returning it.

The DeepSeek adapter receives only bounded tools for listing concepts, reading one concept, searching concept titles and aliases, and reading an exact immutable source version from the internally discovered provenance catalog. It returns structured writes, deletions, provenance references, and executor metadata; it receives no general filesystem capability. The Codex adapter is Codex CLI-only, runs against an isolated candidate workspace seeded from the complete concept baseline, and has its change set derived from the actual workspace diff rather than trusted stdout paths.

A successful result can create, rewrite, rename, merge, split, or delete concept material, but only through validated writes and deletions beneath `Concepts/`. Its citations resolve against both newly prepared source evidence and previously committed immutable source versions. Any malformed output, unavailable narrow read, out-of-scope effect, unsafe path, invalid provenance, or workspace contamination rejects the entire synthesis and yields nothing publishable. <issue id="78b9c71c-5a61-4ba4-9e31-282c5930727a" href="https://linear.app/kenneth-second-brain/issue/SEC-5/deepen-recoverable-batch-publication">SEC-5</issue> remains the sole owner of publication, commit, recovery, finalization, and raw-payload cleanup.

 8. As a vault owner, I want the direct executor to lack unrestricted filesystem reads, so that unrelated vault material and secrets remain inaccessible.
 9. As a vault owner, I want the direct executor to lack unrestricted filesystem writes, so that all proposed changes pass through deterministic validation.
10. As a vault owner, I want the Codex executor isolated from the live vault, so that agentic edits cannot become visible before validation and publication.
11. As a vault owner, I want Codex changes derived from the actual candidate-workspace diff, so that self-reported stdout cannot conceal or invent effects.
12. As a vault owner, I want an unexpected Codex workspace change to reject the whole synthesis, so that contamination is never partially accepted.
13. As a vault owner, I want concept creations and rewrites validated together, so that one unsafe file prevents a partial result.
14. As a vault owner, I want renames represented safely, so that a new target is not published without the matching old path deletion.
15. As a vault owner, I want merges and splits represented safely, so that all resulting writes and deletions share one validation outcome.
16. As a vault owner, I want redundant concept material deletable only inside `Concepts/`, so that cleanup cannot remove source evidence.
17. As a vault owner, I want absolute paths, traversal segments, alternate separators, and empty paths rejected, so that executor paths cannot escape their scope.
18. As a vault owner, I want Unicode-normalized and case-folded target collisions rejected, so that behavior is safe on case-insensitive filesystems.
19. As a vault owner, I want symlinks rejected in candidate and live target ancestry, so that an apparently valid concept path cannot resolve elsewhere.
20. As a vault owner, I want duplicate writes, duplicate deletions, and write-delete conflicts rejected, so that operation order cannot change meaning.
21. As a researcher, I want every article citation to resolve to an immutable source version, so that I can verify the interpretation against stable evidence.
22. As a researcher, I want article line ranges checked against the rendered source, so that citations cannot point beyond the available evidence.
23. As an Obsidian user, I want article links to open at the displayed starting line, so that navigation and visible provenance agree.
24. As a video researcher, I want every YouTube citation to resolve to a known immutable transcript source version, so that the cited evidence is identifiable.
25. As a video researcher, I want YouTube timestamp ranges ordered and bounded by the transcript, so that citations refer to available evidence.
26. As a video researcher, I want each YouTube link’s video ID and start-time parameter to match its displayed citation, so that playback opens at the claimed evidence.
27. As a researcher, I want concepts to cite both newly successful and previously committed source versions, so that synthesis can reconcile new evidence with established interpretation.
28. As a researcher, I want conflicting claims preserved as separately cited interpretation, so that synthesis does not manufacture false consensus.
29. As a concept reader, I want substantive synthesized interpretation to retain valid provenance, so that claims remain auditable.
30. As an operator, I want malformed executor JSON reported explicitly, so that transport failures are distinguishable from validation failures.
31. As an operator, I want unavailable narrow reads reported explicitly, so that configuration or catalog failures are actionable.
32. As an operator, I want timeouts and executor failures reported with executor identity but without secrets, so that failures can be diagnosed safely.
33. As an operator, I want out-of-scope changes and invalid provenance reported with stable failure codes, so that status and retry behavior remain understandable.
34. As an operator, I want a failing synthesis to leave prepared sources, raw HTML, and live concepts unmodified, so that retrying cannot compound damage.
35. As an operator, I want synthesis metadata handed to publication, so that the batch journal records what executor ran and what evidence the result cited.
36. As an operator, I want affected paths and deletions reported deterministically, so that publication and recovery can verify the exact candidate.
37. As an operator, I want adapter-specific model or command details normalized into safe executor metadata, so that reports are comparable without leaking credentials.
38. As an executor maintainer, I want DeepSeek and Codex to satisfy the same behavior contract, so that adapters remain replaceable rather than becoming separate pipelines.
39. As an executor maintainer, I want narrow read results bounded and deterministic, so that adapter behavior is reproducible and context growth is controlled.
40. As an executor maintainer, I want unknown tools, unknown output fields, and malformed operations rejected, so that contract drift fails visibly.
41. As a future maintainer, I want path, provenance, and workspace validation centralized, so that adapters cannot evolve different safety rules.
42. As a test author, I want one high-level synthesis seam with deterministic fake adapters, so that tests assert external behavior rather than transport internals.
43. As a test author, I want real temporary candidate workspaces, so that diff, symlink, case-folding, and contamination behavior is exercised.
44. As a test author, I want equivalent fake DeepSeek and Codex executions to yield equivalent validated results, so that the common contract is proven.
45. As a batch orchestrator, I want either a fully validated synthesis outcome or a structured failure, so that I never coordinate partial adapter state.
46. As the publication module, I want only validated writes, deletions, and result metadata, so that I can journal and publish without reinterpreting executor output.

## Implementation Decisions

 1. Introduce `second_brain.synthesis` as the feature’s only public interface and primary test surface. It exports `build_controlled_synthesis(config)`, `SynthesisRunner.run(batch_id, batch_sources)`, `SynthesisOutcome(change_set, metadata)`, `SynthesisFailure(category, safe_message, executor)`, and the typed metadata, executor identity, and failure-category models. Batch orchestration supplies only the batch identifier and successfully prepared source candidates, then receives either one validated synthesis outcome or one structured synthesis failure.
 2. The synthesis outcome contains a normalized change set plus validated metadata. The change set has only write and delete operations; create and rewrite are writes, while rename, merge, and split are represented by the necessary atomic combination of writes and deletions. Metadata contains the ordered affected paths, ordered deletions, resolved cited source versions, executor identity, and successful validation outcome.
 3. DeepSeek and Codex are transport/execution adapters behind this module. Both produce the same untrusted adapter-result shape and pass through the same normalization and validation pipeline. Neither adapter returns a publishable `ChangeSet` directly.
 4. The existing concept catalog becomes a lightweight index of stable concept descriptors rather than a map of truncated full bodies. Each descriptor exposes the normalized relative path, title, aliases, and outbound concept links needed for discovery. Concept bodies are fetched only through a bounded read capability.
 5. The DeepSeek adapter receives a capability object with exactly four operations: list concept descriptors, read one concept by an identifier returned by the catalog, search titles and aliases with bounded results, and read one exact immutable source version by its catalog identifier. It receives no vault path, generic file reader, shell, environment tool, or write tool. The package discovers both newly prepared and previously committed immutable versions; versionless aliases are invalid.
 6. Narrow reads validate identifiers, enforce their allowed collection, return deterministic ordering, apply explicit size/result bounds, and fail with a structured `narrow_read_unavailable` error. A request for an unknown concept or source is not converted into a broader search.
 7. The DeepSeek adapter is a strict tool-calling loop. It is prompted with identifiers, descriptors, tool schemas, and the output contract, never evidence bodies. It supports at most 16 rounds, 64 total tool calls, 25 search results, 100 KB per body, and the configured total deadline. Unknown tools, malformed arguments, unknown fields, missing immutable versions, and malformed final output fail closed. `deepseek_model` is required explicitly; the retired `deepseek-chat` default is unsupported.
 8. The Codex adapter creates an isolated candidate workspace outside the vault, seeds the complete `Concepts/` baseline once, and invokes Codex CLI with internally constructed safety flags: `workspace-write`, approval policy `never`, `--ephemeral`, `--ignore-user-config`, `--ignore-rules`, `--strict-config`, a fixed candidate directory, no extra writable roots, and schema-validated output. Configuration accepts `codex_executable` and optional `codex_model`; `codex_command` fails with a migration error. Preflight verifies the executable and required flags. Batch evidence is exposed only through immutable candidate-workspace inputs, never by making the live vault reachable.
 9. The Codex adapter treats process stdout as diagnostics and optional structured metadata only. The application snapshots the baseline, walks the completed workspace without following symlinks, and derives writes and deletions from the actual content diff. A claimed stdout path that disagrees with the diff is malformed output; any changed path outside the candidate `Concepts/` tree is workspace contamination.
10. The isolated workspace must begin from a verified regular-file baseline and end with only regular Markdown concept candidates. Created symlinks, modified control files, sockets, devices, unexpected directories, or changes outside the permitted tree reject the entire result.
11. Change-set normalization uses vault-relative POSIX paths. It rejects empty paths, NULs, backslashes, absolute paths, dot or traversal segments, non-Markdown targets, and anything not strictly beneath `Concepts/`. It Unicode-normalizes path components before comparing them and rejects exact, normalized, and case-folded collisions across all writes and deletions.
12. Validation checks both the candidate path and every existing parent/target without following a symlink outside its configured root. Safety is evaluated before any handoff to publication, and one invalid operation rejects all operations.
13. Build one provenance catalog from the successfully prepared batch source candidates plus all previously committed immutable source versions visible in `Sources/`. Each entry is indexed by physical path, source identifier, immutable version, source type, canonical locator, title, content fingerprint, and rendered evidence bounds. Malformed or duplicate committed source identities are a validation failure rather than being guessed through.
14. Adapter results include provenance declarations keyed to the candidate concept path and citation occurrence. The deterministic validator resolves these declarations to exact provenance-catalog entries and derives the final ordered set of cited source versions. This makes YouTube citations version-specific even though their readable Markdown link is video-oriented.
15. Article citations retain the established readable line-range and Advanced URI form. Validation requires the declared source version to be an article, the decoded filepath to equal that version’s physical path, the displayed start and end to be 1-indexed and ordered within the fully rendered immutable Markdown, and the URI line parameter to equal the displayed start.
16. YouTube citations retain the established readable timestamp-range and start-time link form. Validation requires the declared source version to be YouTube evidence, the video ID to match its canonical locator, the displayed timestamps to be non-negative and ordered within the stored transcript bounds, and the link’s integer start-time parameter to equal the displayed start second. A citation that cannot be resolved to exactly one declared source version is rejected.
17. Citation validation accepts both new candidate source versions and previously committed immutable versions. It validates candidate sources from their final deterministic rendering, so physical article lines match what <issue id="78b9c71c-5a61-4ba4-9e31-282c5930727a" href="https://linear.app/kenneth-second-brain/issue/SEC-5/deepen-recoverable-batch-publication">SEC-5</issue> will publish.
18. Concept Markdown must use UTF-8-compatible text, LF endings, and a trailing newline. Binary files and image candidates are invalid. Existing concept structure is otherwise deliberately unconstrained; this issue does not impose a concept template.
19. The executor policy requires meaningful disagreements to remain in separate passages with separate citations. Deterministic validation proves that each supplied citation resolves and remains associated with its passage; semantic conflict detection remains an executor responsibility and is covered with deterministic conflict fixtures rather than a false claim of automatic truth adjudication.
20. Structured failures use stable categories at minimum for malformed executor output, adapter execution failure, timeout, unavailable narrow read, invalid operation, path collision, out-of-scope change, symlink escape, workspace contamination, invalid provenance, and invalid concept Markdown. Messages include safe context and executor identity but exclude prompts containing evidence, credentials, environment contents, and secret headers.
21. A failed controlled synthesis returns no change set. Successfully prepared jobs remain durably `source_ready`; they are not moved to completion. The failure does not mutate live `Concepts/`, live `Sources/`, queue material, raw HTML, Obsidian settings, publication state, or Git state. External diagnostic workspace retention may be configurable, but retained work is never publishable without a fresh full validation.
22. Successful metadata is passed unchanged as validated data into <issue id="78b9c71c-5a61-4ba4-9e31-282c5930727a" href="https://linear.app/kenneth-second-brain/issue/SEC-5/deepen-recoverable-batch-publication">SEC-5</issue>’s publication handoff and stored with the publication journal or its associated synthesis record. Publication remains responsible for candidate materialization, rollback snapshots, the local commit, recovery, finalization, and cleanup; it does not rerun synthesis validation.
23. Executor identity is normalized to adapter kind plus safe implementation/model identity and execution version where available. Secrets, full command environments, API keys, and raw prompts are never journaled.
24. Ordering is deterministic: catalog listings, search ties, normalized operations, affected paths, deletions, citations, and cited source versions have stable sort rules. This allows equivalent deterministic adapter fixtures to yield equivalent validated result semantics.
25. Existing no-op behavior remains a valid adapter result: it returns an empty validated concept change set with executor metadata. The enclosing batch may still publish successful source candidates; synthesis does not manufacture a concept change merely to make the result non-empty.
26. Assumptions: <issue id="7fe77ea9-46e8-47d3-a6c6-a66d7da54197" href="https://linear.app/kenneth-second-brain/issue/SEC-7/deepen-immutable-source-preparation">SEC-7</issue> supplies validated immutable source candidates and version-specific physical paths; <issue id="78b9c71c-5a61-4ba4-9e31-282c5930727a" href="https://linear.app/kenneth-second-brain/issue/SEC-5/deepen-recoverable-batch-publication">SEC-5</issue> accepts an already validated synthesis outcome and owns all live-vault mutation; the configured state directory is outside the vault; and the existing batch lock prevents a second ingestion process. If version identity is ambiguous before <issue id="7fe77ea9-46e8-47d3-a6c6-a66d7da54197" href="https://linear.app/kenneth-second-brain/issue/SEC-7/deepen-immutable-source-preparation">SEC-7</issue> is complete, provenance validation fails rather than selecting a source version implicitly.
27. ADR-0001 records the trust boundary: repository-owned adapters are trusted implementation, while model responses, tool calls, and Codex workspace effects remain untrusted until normalized and validated. Third-party in-process adapters are unsupported. Any later durable policy change must be recorded in a separate ADR rather than hidden in adapter code.

## Testing Decisions

 1. The primary feature seam is the public `second_brain.synthesis` interface. Tests provide configuration, a batch identifier, successful source candidates, deterministic adapter doubles, and real temporary filesystems, then assert only the returned validated outcome or structured failure. Catalog loading, provenance discovery, and workspace creation remain package-owned behavior.
 2. The existing public-seam style is prior art: temporary vaults and state directories, real local filesystem and Git behavior where relevant, and deterministic adapters. Exercise DeepSeek with a fake HTTP transport and Codex with a fake executable so strict tool dispatch, execution limits, safety flags, and observed workspace effects are tested without coupling to private helpers or prompt prose.
 3. A small number of integration tests cross `BatchRunner.run` to prove that a valid synthesis outcome reaches <issue id="78b9c71c-5a61-4ba4-9e31-282c5930727a" href="https://linear.app/kenneth-second-brain/issue/SEC-5/deepen-recoverable-batch-publication">SEC-5</issue> and that a failed synthesis produces no publication. The controlled-synthesis seam owns the exhaustive feature matrix.
 4. The same deterministic scenario is exercised through fake direct and Codex adapters and must yield equivalent normalized writes, deletions, cited source versions, affected paths, executor identity categories, and validation status.
 5. DeepSeek-adapter tests prove that listing, reading one concept, searching titles/aliases, and reading an exact immutable source version are available, bounded, and deterministic; attempts to use versionless identifiers, read unknown sources, unrelated files, the environment, or generic paths fail.
 6. Direct-adapter tests prove that full source and concept bodies are not present in the initial request and can be obtained only through the narrow read capabilities.
 7. Codex-adapter tests use baseline and completed temporary workspaces to prove that actual creations, rewrites, and deletions are captured even when stdout omits them, and that fabricated stdout paths are not accepted.
 8. Codex-adapter tests prove that changes outside `Concepts/`, unexpected deletions, control-file changes, symlinks, and other non-regular workspace entries reject the entire result.
 9. Operation tests cover create, rewrite, delete, rename, merge, and split semantics, including mixed operations in one result.
10. Path tests cover absolute paths, empty paths, dot and traversal components, backslashes, NULs, non-Markdown targets, exact duplicates, write-delete conflicts, Unicode-normalized collisions, case-folded collisions, candidate symlink escapes, and live-parent symlink escapes.
11. Article provenance tests cover a valid newly prepared source, a valid previously committed version, unknown physical paths, wrong source type, line zero, reversed ranges, ranges beyond the rendered file, mismatched displayed and URI start lines, malformed URI encoding, and a provenance declaration that disagrees with the Markdown citation.
12. YouTube provenance tests cover a valid new transcript, a valid committed transcript version, invalid video IDs, a video ID that disagrees with the declared version, negative or reversed timestamps, timestamps beyond transcript bounds, wrong start-time links, ambiguous source versions, and a missing provenance declaration.
13. Conflict fixtures contain opposing claims and require separate passages with separately resolvable citations. Tests assert the observable result structure and provenance, not model reasoning or private prompt text.
14. Markdown tests cover LF endings, trailing newline, text-only candidates, and rejection of binary/image candidates while allowing ordinary concept organization without a rigid frontmatter or section template.
15. Failure tests cover malformed JSON, unknown output fields, malformed operation records, adapter timeouts, process/API failures, unavailable narrow reads, and malformed committed source catalog entries. Each returns the expected stable failure category and no publishable change set.
16. Isolation tests start from durably prepared `source_ready` jobs, then snapshot the live vault, raw HTML, prepared candidates, SQLite job state, and Git history before a failing synthesis. They prove the source-ready state and candidate remain available for retry while publication, completion, cleanup, and Git remain unchanged.
17. Metadata tests prove deterministic ordering and the presence of affected paths, deletions, exact cited source versions, normalized executor identity, and successful validation outcome, while proving secrets and evidence bodies are absent.
18. No-op tests prove an empty concept change set remains valid and does not prevent successfully prepared batch sources from proceeding through publication.
19. The final verification run includes focused controlled-synthesis tests, the complete suite, the repository’s configured static and formatting checks, and one fixture batch for each adapter using deterministic transport doubles.

## Out of Scope

* Selecting or benchmarking a production DeepSeek model, Codex model, or prompt strategy.
* Granting either executor unrestricted filesystem, shell, environment, network, or vault access.
* Source discovery, extraction, rendering, immutable version allocation, image transcription, or transcript acquisition; <issue id="7fe77ea9-46e8-47d3-a6c6-a66d7da54197" href="https://linear.app/kenneth-second-brain/issue/SEC-7/deepen-immutable-source-preparation">SEC-7</issue> owns those responsibilities.
* Candidate publication, rollback, Git commit creation, recovery, SQLite finalization, or raw-payload cleanup; <issue id="78b9c71c-5a61-4ba4-9e31-282c5930727a" href="https://linear.app/kenneth-second-brain/issue/SEC-5/deepen-recoverable-batch-publication">SEC-5</issue> owns those responsibilities.
* Remote Git behavior, pushes, branches, pull requests, or hosted CI configuration.
* Redesigning the concept taxonomy, imposing a fixed concept-note template, or automatically deciding which disagreements are philosophically correct.
* Installing or configuring Obsidian, Advanced URI, DeepSeek credentials, Codex credentials, or YouTube OAuth.
* Vector databases, embeddings, hosted retrieval, a daemon, or broader RAG infrastructure.
* Migrating existing concept prose or repairing pre-existing invalid citations outside the concepts actually changed by this synthesis result.
